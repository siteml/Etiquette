# Series generation — design (DRAFT 1)

Status: **design draft, not implemented.** This document is expected to go
through multiple passes before any code lands. Open questions are marked
`[?]` and collected at the end.

## Goal

Print a *run* of labels whose content varies per label, with the varying
values coming from anywhere on a spectrum:

- hand-set / operator-entered (start + count, start–end)
- local counter files (the existing counter service)
- reserved through a database / REST endpoint / Epicor Kinetic Function
  (atomic server-side allocation)
- generated by a data source — the rows of a BAQ / REST result set

and with the completed run **recorded** as a transaction in one or more
places. Reprinting any previously printed run (or a sub-range of it) must
be possible without re-consuming anything.

## Vocabulary

- **query** (`etiq:query`) — *read-only* parameterized reference data:
  one fetch, one row, fields read columns. The element shipped in 0.7.0
  spelled `etiq:source`; the rename to `etiq:query` is unreleased and
  ships with the next release, whichever number that ends up being.
  Both spellings parse.
- **series** (`etiq:series`, new) — a *transaction pipeline*: inputs →
  allocation/generation of an ordered row set → per-label resolution →
  recording of what was printed. Data flows both ways; a query never
  writes.
- **provider** — the strategy that produces the series' rows.
- **run** — one execution of a series: N labels, their rows, and run
  context (`index`, `count`, timestamps, dataset, operator inputs).
- **manifest** — the durable record of runs: rows *as printed*. The
  replay source for reprints and the input to confirm-style record
  targets.
- **record target** — a destination told about the completed run
  (manifest is always implicitly first; others: counter advance, Epicor
  Function, REST call, ...).

## The core model: rows in, rows out

Every provider, asked for a run of N, yields **rows** — named columns,
not single values. Manual and counter providers yield one column
(`value`) plus run context; a reservation Function may return richer rows
(`{serial, lot, checkDigit}`); a source-generated series IS rows.

Consumption is the existing binding model: any number of fields declare
`source="series" series="Box" column="serial"`, each applying the
existing transform vocabulary (compose, maps, `format=`, `case=`,
`pad=`). Any input can therefore feed any output, and multiple outputs —
**through the closed transform vocabulary only**. No expression language;
templates stay auditable data.

Reprint follows from the model: the manifest stores rows verbatim, so
replaying rows 40–55 is identical for every provider — deterministic or
consuming.

## Providers (initial set)

| provider    | rows come from                              | consuming? |
|-------------|---------------------------------------------|------------|
| `manual`    | operator/template start (+count/end)        | no         |
| `counter`   | local counter service, `ReserveRange(n)`    | yes        |
| `epicor-fn` | Kinetic Function call (atomic UD increment) | yes        |
| `rest`      | REST endpoint reservation                   | yes        |
| `query`     | all rows of a declared query's result set   | no         |

Consuming = asking twice yields different values; these REQUIRE the
manifest for reprint. Deterministic providers get manifest entries too
(uniform replay + audit).

Proposed Epicor Function contract (we define, site implements):
request `{counterName, count, context...}` → response `{start, end}` or
row array. `[?]` exact shape — one atomic call per run is the invariant.

## Recording

```xml
<etiq:series name="Box" provider="epicor-fn" connection="Epicor"
             function="LabelLib/ReserveSerials"
             count="{Qty}" param-Job="{JobNum}">
  <etiq:record to="manifest"/>                                   <!-- implicit anyway -->
  <etiq:record to="epicor-fn" connection="Epicor" function="LabelLib/ConfirmPrinted"/>
</etiq:series>
```

- Inputs: `count=`/`start=`/`param-*` values are literals or `{Field}`
  references — same mechanism as queries. Multiple inputs fine.
- Allocation *reserves*; recording *commits what actually printed*. A
  cancelled/failed run shows the difference in both places — that IS the
  gap policy, made visible instead of configured away. `[?]` whether an
  explicit void/return record target is also wanted.
- Record targets run after the print job completes. `[?]` semantics on
  partial print (driver error at label 30 of 100): record 29? prompt?

## Manifest

Durable, append-only store of runs: template id, series name, provider,
dataset, operator, timestamps, and the row set as printed.

- `[?]` location: per-machine (%APPDATA%\Etiquette\manifest\*.jsonl) vs
  central (a record target IS the central copy — manifest stays local,
  central copies are additional targets?). Leaning: local JSONL always;
  central = record targets.
- `[?]` retention / rotation.
- Reprint UI reads it: pick run → pick row range → print (marked as
  reprint in the manifest; reprints never re-run allocation or
  record-to-remote — `[?]` unless a site wants reprint notifications?).

## Template shape (draft)

```xml
<etiq:series name="Box" provider="counter" counter="ACME-BOX"
             count="{Qty}"/>
<etiq:field name="BoxSerial" source="series" series="Box" column="value"
            format="000000"/>
<etiq:field name="BoxOfN" source="auto" value="labelindex"/>  <!-- run context -->
```

- `labelindex`/`labelcount` auto kinds (reserved since 0.2) are
  implemented as run context.
- `[?]` multiple series per template: allowed? (e.g. box serial +
  pallet serial). Presumably yes — one run each, same count? Or
  master/detail counts? Needs a pass of its own.
- `[?]` interaction with Print All (list rows × series) and with panel
  copies/collation. Straw answer: series defines the pages; copies
  multiplies them; grouped default; Print All + series mutually
  exclusive per job until a real need appears.

## UX (sketch — needs its own pass)

- Data panel (etiq:panel) grows series controls: count/start inputs
  (per provider), a run summary line ("will print 000123–000222"),
  and a Reprint… button opening the manifest browser.
- F4: a Series tab in the style of Sources/Panel.
- Design mode: sample rows, no allocation ever.

## Staging (each stage shippable)

1. **Manifest + manual + counter (with `ReserveRange`)** — proves the
   whole pipeline: run → print → record → reprint UI.
2. **epicor-fn + rest providers, record targets** — the transactional
   spectrum; Function contract published.
3. **query-rows provider** — series from a result set; needs queries
   extended from first-row to all-rows.
4. Polish: multiple series, Print All interplay, central manifest
   targets, partial-print policy hardening.

## BarTender 10.1 parity

Requirements sourced from Seagull's published docs (the serialization
white paper and the 10.1 what's-new) — feature-set parity only, no
implementation internals. How each maps onto this design:

| BarTender 10.1 capability | Series design answer |
|---|---|
| Numeric / alphabetic / alphanumeric / hex / custom sequences | existing `format=`/`alphabet=` machinery (custom base = custom alphabet) |
| Lowercase alphanumeric; exclude look-alikes (I, O) | **gap** — add lowercase + exclusion options to `alphabet=` |
| Preserve character width through rollover | **gap** — `format=` fixed-width pad exists; needs explicit rollover tie-in |
| Increment up/down, any step | provider `step=` (negative = decrement) |
| Step / interval / reset-limit from a data field | `{Field}` values on provider attrs — already in the draft |
| Increment per item / per page / per job / on data change | **new concept**: `advance=label\|job\|change:Field` on the series (per-page N/A — labels are pages) |
| Reset at limit (with reset target) | **new concept**: `<etiq:reset at="…" to="…"/>` rules |
| Reset per job / per record / on data change / on schedule (day/month/year) / manual | same reset-rule vocabulary: `every="job"`, `change:Field`, `schedule="day\|month\|year"`, plus a manual reset in the counters UI |
| Remembers position between jobs, incl. remaining interval at step > 1 | counter provider persistence (store position, not last-printed) |
| Global counters (System Database; network-shared) | shared providers: epicor-fn / rest / central counter — strictly stronger |
| Serials-per-job × copies-per-serial | series `count=` × panel copies/collation |
| Decoration (prefixes, dashes, date+serial in one object) | compose — already covered |

Net-new items for the schema from this table: `advance=`, reset rules,
`alphabet=` options (lowercase, exclusions), preserve-width rollover,
negative step. All fit the provider/row model without touching the
manifest/record core.

## Open questions (roll-up)

1. Epicor Function contract shape (range vs row array).
2. Counter files: shared network counters, or is "shared" always the
   remote providers' job?
3. Partial-print recording semantics.
4. Void/return record target for cancelled reservations?
5. Manifest location/retention; central copies as record targets?
6. Multiple series per template; master/detail runs.
7. Series × Print All × copies/collation interplay.
8. Reprint of consuming series: any site need to notify remote systems
   of reprints (record target on replay)?
9. Parity items (table above): exact `advance=`/reset-rule syntax;
   where the manual "Reset Now" lives (counters UI vs data panel);
   whether scheduled resets belong to the counter store or the series.
